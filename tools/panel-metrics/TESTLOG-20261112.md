## 2. 根因备忘

内置 "Pushed value" 控件（`type:"push"`）的颜色**只由 payload 的 `level` 字段驱动**
（ok=绿 / warn=橙 / error=红），gauge 的 `max` 只定义满量程。此前 `gpu_power` 恒绿
= 脚本推它时从来没带 `level`；`strata_ctx` 会变色就是因为它带了。

## 3. 充电与换口实测（本轮顺带拿到的硬数据）

### 7.1 “进度条怎么不动”的口径结论（别再当 bug 查）

1. **reading**：`prompt_read/prompt_total` 只在 `state=="reading" && engine.progress` 时才填
   （`serve/server.py` L5652 + L5671）；`engine.progress=(read,total)` 由引擎 **PP 心跳行**每读完
   一个 prefill chunk 更新一次（L2876/L1887）。本机 `--prefill auto:32768` ⇒ 实测就是 32,768 一跳：
   `32,768 → 65,536 → 98,304 → 131,072 → 142,611 / 142,616`。**prompt 不足一个 chunk 时 total=None**
   ⇒ detail 退成 `24,052 tokens`、进度 0%；引擎自带 Monitor 也一样（用户原图那台在读 167,816，是多 chunk）。
2. **generating**：`pct = generated / max_tokens`，客户端常给 `max_tokens=32000`，实际输出几百到几千
   ⇒ 1–3%，肉眼近似“贴地不动”，亦为引擎原样。Strata 的 **React 版** `Monitor.tsx` 对无进度值用
   `indeterminate`（serve 内置页没做）——想在面板上“看着在动”，可选升级=对 `pct<2%` 的 generating
   加一条缓慢扫动的高光，数字口径不动。
3. timer 5s 一跳不是瓶颈：reading 的数据本身按 chunk 台阶变，改 2s 只让它更及时一点。（15:3x 已改 1s，见 §8）

## 8. 15:3x 进度条行程改造（用户反馈“reading 段手机上几乎不动”，要求像 strata 面板那样走到头）

结论：**引擎的 reading 进度天生是 chunk 级台阶**，不是控件 bug；真正的差别在**刷新率**，另外顺手把
generating 段的分母换掉了。

- 数据源实测（`serve/server.py` L5652 + L5671；`engine.progress=(read,total)` 来自引擎 **PP 行**，
  L2876 每读完一个 prefill chunk 才打一次）：144,291 token 的全新 prompt，`prompt_read` 一路是
  `32,768 → 65,536 → 98,304 → 131,072 → 142,611`（`total=144,291`）。浏览器里的 Monitor **每秒刷一次**
  ⇒ 观感是“一路走到头”；我们当时 **5s 推一次** ⇒ 一个 40s 的 reading 只采到 2–3 个点、还常被
  `ttl 20s` 的旧值盖住 ⇒ 手机上就是“几乎不动”。（用户原图里 `101,214 / 167,816` 不是 32768 的整数倍，
  说明 chunk 会随复用边界变小 ⇒ 台阶更密，同理。）
- **改①刷新率**：`pb-strata-push.timer` `OnUnitActiveSec=5s → 1s`（备份 `temp/pb-push-1s-*/`）。为扛住 1s 节奏，
  `gpu_stats()` 增加 `/tmp/pb_gpu_cache.json` 缓存——**nvidia-smi 每 5s 才真查一次**（满载时它自己要先等
  0.2–0.5s 的 GPU 锁）。实测 `at` 的 age 稳定在 0.1–2.6s。
- **改②generating 分母**：不再用 `max_tokens`（本会话客户端给的是 **359,945** ⇒ 条子永远贴地）。脚本新增
  `out_est` = 最近 8 个请求 `output_tokens` 的 **p75，下限 512**，控件优先用它。真机实测一条 900-token
  流式请求：面板 `pct 26% → 45%`，绿条明显爬升，而 `541 tokens · 116.0 tok/s` 的数字口径一点没改。
- **改③无分母兜底**：reading 时 prompt 不足一个 chunk（`total=None`）、以及 generating 但还没有历史样本，
  改成 **32% 淡底 + 一块扫光**（即 Strata React 版 `Monitor.tsx` 的 `indeterminate` 做法，serve 内置页没实现）。
  两个坑：① `bar` 上带内联 `style="width:0%"`，class 里的 `width:100%` 顶不掉，**必须 `!important`**；
  ② 扫光位移幅度先给 420% 结果静态截图里几乎抓不到，收窄到 330% 才稳定可见。
- 离线核对：`gen_verify.mjs` 新增 `read_no_total / gen_indet / gen_est` 三个 case，430×158 下三态渲染正确、
  字号 13px 无溢出。真机 generating 45% 已截屏确认（`temp/pb_state_gen2/g3.png`）。
- 回滚：`cp temp/pb-push-1s-*/pb-strata-push.timer.before ~/.config/systemd/user/pb-strata-push.timer`
  （或把 `1s` 改回 `5s`）+ `systemctl --user daemon-reload && systemctl --user restart pb-strata-push.timer`；
  脚本回 `temp/pb-push-1s-*/pb_strata_push.py.before`；控件重贴旧文本即可（`out_est` 对旧控件是惰性字段）。

## 9. 15:5x VRAM 控件：`vram_pct` 回归（内置 Pushed value 风格，不写 HTML）

- 需求：风格跟 `gpu_power` 一致 ⇒ 只用内置 **Pushed value**：Add → Pushed value →
  `key=vram_pct`、`style=gauge`、**max=100**（跟 gpu_power 的 max=350 同理，颜色由 payload 的 `level` 驱动）。
- payload：`{value:96.3, unit:"%", progress:96.3, sub:"23.1 / 24.0 GB · 912 MiB free", level:"ok", ttl:20}`。
- 数据来源：`gpu_stats()` 的**同一次** nvidia-smi 查询顺带 `memory.used,memory.total`（返回改成四元组
  `(draw, limit, used, total)` 并整体缓存），所以 1s 的 timer 节奏下显存也是 5s 才真查一次，零额外开销。
- **顺手修真 bug**：缓存命中只判 `ts` ⇒ 沿用只有瓦数的老缓存时 `used/total` 是 None、`vram_pct`
  会**静默不推**（现场就是 `vram=n/a`）。现在要求 `used && total` 也在才算命中。
- **着色口径不按百分比**：实测这台常驻就是 `23,664 / 24,576 MiB`（96.3%，free 只剩 912 MiB——引擎按
  `free − --vram-reserve-mib 768` 的地板把 expert arena 填满），照 gpu_power 那种比例阈值或 90/95%
  都会**常年红色**、失去告警意义。改成按“还剩多少 MiB”分级，**最终阈值由用户 15:5x 定为
  `VR_WARN_FREE=2000 / VR_ERR_FREE=500`**（我先给的是 700/400）⇒ 语义变成“余量不足 2G 就橙”，
  所以常驻的 912 MiB 本来就显示橙色，只有跌进 500 MiB 以内才转红（引擎自留地板约 523 MiB）。
  断言过 `2100→ok / 1500→warn / 912→warn / 480→error`。
- 实况：push keys 六个（+`vram_pct`），`vram_pct.age=0.8s`，与 `nvidia-smi` 真值逐 MiB 一致；
  `~/bin` md5 `4cb5cac4`。顺带记录：`gpu_power` 当时 331.6W ⇒ `level=error`（350W 墙的 95%）✓ 着色正常。
- **15:5x 值从百分比改成 GB**（用户："把值从百分比改成 GB，比如 23.5"）：`value = used_GB`（一位小数，实测
  `23.1`）、`unit:"GB"` ⇒ **面板里 gauge 的 max 必须从 100 改成 24**，否则环会画到爆。key 故意仍叫 `vram_pct`
  （免得用户重新填 key），`progress` 继续带百分比供其它 style 用，`sub` 改成 `96.3% · 912 MiB free`
  把百分比和余量这两个信息留住。level 判定完全不受影响（还是按 free MiB）。
- **随即 key 改名 `vram_pct` → `vram_gb`**（用户："key 改成 vram_gb 吧，我同步调一下"）⇒ 面板控件里的 key 由用户
  同步改；旧 key 当场 `curl -X DELETE http://127.0.0.1:8765/api/push/vram_pct` 清掉（不删也会在 20s ttl 后自己走）。
- 回滚：`curl -X DELETE http://127.0.0.1:8765/api/push/vram_gb` + 脚本回 `temp/pb-vram-*/pb_strata_push.py.before`，
  面板删掉该控件。

## 10. 16:0x `gpu_power` 改按**绝对瓦数**着色

- 用户指定：**≤100W 绿 / 100–300W 橙 / >300W 红**。原来是按 `power.limit` 的比例（50%/80% ⇒ 350W 墙下
  175W/280W 才跳色），跟直觉不符（245W、331W 在他眼里就该是橙和红）。
- 实现：文件头 `GW_WARN, GW_ERR = 100.0, 300.0`，判定 `gw > GW_ERR ? error : gw > GW_WARN ? warn : ok`
  ⇒ 恰好 100W 绿、恰好 300W 橙、301W 起红。`power.limit` 仍随同一次 nvidia-smi 查询进缓存，但**不再参与
  着色**；以后想换回比例口径一行即可。
- 本机对号入座：待机 <100W 绿；轻载（实测 132.6W）橙；prefill/decode 满载 330–341W 红。
- 实况核对：断言 `[(60,ok),(100,ok),(101,warn),(300,warn),(301,error)]` 全对，推送的 `level` 与当前瓦数一致。
